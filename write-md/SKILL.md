# Write Markdown Tutorials

## 核心目标

把读者带到一个可验证的结果：读者知道这篇教程是否适合自己，能完成主任务，理解关键取舍，并能在失败时自救。

- 默认在对话中直接交付完整 Markdown，不创建文件。
- 默认跟随用户使用的语言；无法判断时使用简体中文。
- 默认服务“有兴趣但不一定有经验”的读者，同时让高手能快速定位参数、原理和取舍。
- 只写完成任务所需的内容，不为了显得完整而堆叠章节。
- 让 Markdown 形式服务信息层级，不把装饰当作内容。

## 工作流程

### 1. 先理解材料

先读取用户提供的网页、文档、本地文件和上下文，再决定是否需要提问或补充调研。

- 只有主题：围绕读者任务查找最新的一手资料。
- 提供网站：先读目标页面，再用官方文档补足关键缺口或核实时效性事实。
- 提供文档或本地文件：阅读所有相关部分，保持原有术语、版本和范围。
- 提供混合资料：对照来源；冲突时优先采用更权威、更新的一手来源，并说明差异。
- 内容无法访问：明确指出缺口，不根据标题、摘要或想象补写正文。
- 用户限制资料范围：严格遵守，不擅自联网扩展。

只在缺失信息会改变教程方向时提问，例如同名工具、互不兼容的平台或完全不同的目标读者。其他缺口使用最保守的合理假设，并在教程开头简短说明。

### 2. 建立教程契约

在写作前内部确定以下事项，不必机械地把它们全部写成可见章节：

- **任务结果**：读者完成后能够做什么，如何确认成功。
- **读者基线**：默认会什么，哪些术语必须首次出现时解释。
- **范围边界**：本篇解决什么，不解决什么。
- **环境条件**：工具、平台、版本、账号或材料要求。
- **证据状态**：哪些是来源事实，哪些是推断，哪些是建议。

若无法写出明确的成功结果，先收窄教程任务，不要开始堆砌背景知识。

### 3. 选择教程形态

根据任务选择最短的有效结构：

- **操作型**：准备条件 → 连续步骤 → 结果验证 → 故障排查。
- **概念型**：问题与心智模型 → 关键概念 → 完整例子 → 应用与边界。
- **混合型**：先给可执行主线，再在相关步骤附近解释原理和取舍。
- **比较型**：先给选择结论，再按“适合谁、优势、代价、何时不用”分别说明方案。

不要把每篇教程都写成同一模板。不存在真实内容的章节应直接省略。

### 4. 组织正文

优先从下列质量要素中动态组装文章：

1. 使用一个具体、结果导向的一级标题。
2. 用两到四句话说明痛点、价值和本篇能带来的结果，避免泛泛的行业背景。
3. 用简短引用块说明“完成后你将获得什么”，适合人群明显时同时标明适用对象。
4. 只在确有门槛时加入前置准备。
5. 将主任务写成连续、可执行的步骤；每个关键步骤覆盖：
   - 做什么；
   - 为什么这样做；
   - 应该看到什么结果。
6. 在最接近问题发生的位置加入验证点、易踩坑或进阶说明，不把所有提醒堆到文末。
7. 至少使用一个贯穿全文的完整例子；优先于多个互不相干的片段。
8. 加入真实工作中的应用方式，说明教程能力如何进入现有流程。
9. 只收录高概率或高代价的问题；按“现象 → 原因 → 修复”编写。
10. 以可执行的检查清单或下一步收尾，不重复全文。

教程不一定要显示以上十项，但必须让读者能完成任务并验证结果。

## 同时服务新手与高手

保持一条连续的新手主路径，不要分别重写“入门版”和“高手版”。

- 在术语第一次出现时用一句话解释，之后使用准确术语。
- 给出可复制的命令、配置或示例，并明确占位符需要替换什么。
- 在高风险步骤后立即给出预期结果和检查方法。
- 把底层原理、参数选择、替代方案和性能取舍放在相关步骤后的 `🧠 进阶理解` 中。
- 只有存在真实选择时才介绍替代方案，并明确推荐默认值。
- 如果用户已表明经验水平，压缩其已知内容，不强迫高手阅读基础常识。

## 控制篇幅与密度

按任务复杂度写到“足以成功”为止，不追求固定字数。

- 狭窄任务保持少量章节和短步骤，不补写历史、行业趋势或无关原理。
- 复杂任务保持三到七个主要步骤；更多内容拆成“核心路径”和“深入理解”。
- 每段只承担一个意思，通常控制在两到四句话。
- 一个完整示例优先于多个残缺示例。
- 删除重复总结、同义改写、显而易见的解释和无行动价值的铺垫。
- 保留会改变操作、判断或结果的信息；其余内容不写。

## 事实、引用与时效

- 对版本、价格、限制、功能支持、政策和其他可能变化的事实进行当前核实。
- 优先使用官方文档、原始论文、标准或产品公告；搜索结果只用于发现来源。
- 将链接放在它所支持的句子附近，使用描述性链接文字。
- 明确区分“来源明确说明”“根据证据推断”和“建议采用”。
- 结尾只列出正文实际使用过且值得读者继续查看的来源，不堆砌链接。
- 不为常识性写作建议添加无意义引用，也不伪造来源、版本或测试结果。

## 飞书友好的 Markdown

默认生成可直接复制到飞书云文档的保守 Markdown 子集。

- 全文只使用一个一级标题；正文优先使用二、三级标题，不建立过深层级。
- 使用有序列表表达流程，无序列表表达并列信息，任务列表表达验收项。
- 使用以下带标签引用块建立视觉节奏：
  - `> 🎯 完成目标`
  - `> 💡 提示`
  - `> ⚠️ 易踩坑`
  - `> ✅ 验证结果`
  - `> 🧠 进阶理解`
- 只在确有导航价值时使用 Emoji，同一小节不要堆叠多个图标。
- 为代码块标注语言；提示词使用 `text` 或 `markdown`，命令使用对应 shell，数据使用实际格式。
- 使用行内代码标记命令、参数、文件名、字段名和界面中的精确值。
- 使用标准 Markdown 链接；分隔线只用于少数重要阶段转换。
- 在参数速查、方案对比、输入输出映射、故障排查等需要精确横向比较时使用 Markdown 表格。
- 保持表格紧凑：优先控制在二到五列，单元格使用短句；步骤、长解释和多段代码仍使用正文或列表。
- 当表格在窄屏中难以阅读，或每个方案需要较长解释时，改用 `### 方案 A`、`### 方案 B` 等短小卡片。
- 不使用原始 HTML、`<details>`、Mermaid 或依赖特定插件的提示框。
- 只有当关系无法用短段落或列表说明时，才使用紧凑的纯文本图，并放入代码块。

用户明确指定其他发布平台、表格、Mermaid 或特殊语法时，以用户要求覆盖这些默认值。

## AI 教程分支

当主题涉及模型、提示词、Agent、AI 产品、AI 编程或生成式图像、音频、视频工作流时，在列提纲前完整读取 [references/ai-tutorial-patterns.md](references/ai-tutorial-patterns.md)。只采用与当前任务有关的模式，不强制加入所有 AI 章节。

非 AI 主题不要读取或套用该参考文件。

## 交付前质量门

交付前逐项检查并直接修正问题：

- **结果检查**：标题和开篇是否承诺了明确结果，结尾是否能验证它。
- **新手检查**：没有额外背景的人能否按顺序完成，是否存在跳步或未解释术语。
- **高手检查**：能否快速找到关键参数、原理、取舍和边界，而不必读重复内容。
- **证据检查**：时效性事实是否核实，事实、推断和建议是否分清，链接是否真的支持相邻陈述。
- **示例检查**：示例是否完整、可复制、占位符明确，并与正文步骤一致。
- **故障检查**：是否覆盖最可能阻塞成功的问题，而不是罗列低价值 FAQ。
- **飞书检查**：标题层级、列表、引用、表格和代码围栏是否完整；表格是否紧凑易读；是否残留 HTML、Mermaid 或平台扩展语法。
- **精简检查**：删除一段后是否仍能完成任务；如果可以且不损失理解，就删除。

## 交付方式

- 默认直接输出教程正文，不加“下面是教程”等元话语，不把全文包进代码块。
- 默认不创建 `.md` 文件；用户明确要求文件、路径或可下载产物时再创建。
- 用户要求只使用所给材料、保留原文结构或遵循特定模板时，优先遵守该约束。
- 若证据存在无法解决的缺口，在相关位置简短说明，不用自信语气掩盖不确定性。
