# 提问契约：把治理问题翻译成人能选的话

闸门一项都不能少；变的是**怎么问人**。面向用户的确认、停点和提案，必须先经过本文件，再使用内部术语。

## 必须遵守

1. **生活语言 + 项目实例。** 先说这件事在这个项目里意味着什么，再给文件名、出现次数或截图位置。不要把登记字段名直接丢给用户。
2. **每题给带理由的推荐项**，并写明「不确定就选推荐项」。推荐必须来自本次审计证据，不能凭偏好。
3. **一次最多 3～4 个问题。** 能从证据推断的先写成「我准备这样做」，只请用户确认或否决，不要让用户填空。
4. **术语第一次出现时带一句话类比。** 用户已经用过该术语时除外。类比以 [SKILL.md](../SKILL.md) 的 30 秒心智模型为准。
5. **宿主支持结构化提问时优先选择题**（如 Cursor `AskQuestion`）。开放问答只用于证据不足、无法列出选项的停点。
6. **不要把 JSON 报错原文直接贴给非专业用户。** 先说影响和可选动作；需要排错时再附机器信息。

## 术语翻译对照

问用户时用右列；写 `design-system/`、脚本参数和 Agent 规则时仍用左列。

| 内部用语 | 对人怎么问 |
| --- | --- |
| 权威来源 | 以后改颜色、间距时，以哪一份现有文件为准？ |
| Core | 全站默认装修：所有页面共用的底色、字体、间距。 |
| Primitive | 调色盘里的具体色号或尺寸，本身不说明用在哪。 |
| Semantic | 用途名，例如「主按钮背景」，指向调色盘里的某个值。 |
| Component 例外 | 某一个组件可以和全站规则不一样；默认不要建。 |
| Scope / 局部规范 | 个别房间的特殊装修，只作用于已标明的页面。 |
| Theme | 同一界面的白天／夜晚灯光，不是另一组页面。 |
| 激活方式 | 切换暗色（或其它模式）时，技术上改的是 class、data 属性，还是系统偏好？ |
| 运行时所有者 | 现在是哪段代码（或手动 class）在切换这个模式？没有开关就说「还没有开关」。 |
| Drift | 某面墙上多出来的一次性色值或尺寸，先记下来，不自动变成全站规则。 |
| `reference-only` | 先登记作参考，不接到真实页面上。 |
| 写入闸门 | 动手改文件前，需要你点头的那几件事。 |

## 问法对照

| 不要这样问 | 可以这样问 |
| --- | --- |
| 请选择权威来源。 | 项目里有两处都在定义颜色：`src/styles/main.css`（8 个变量）和 `tailwind.config.js`。以后改颜色以哪份为准？我建议选 `main.css`，因为页面实际引用它。不确定就选推荐项。 |
| 请确认受控的根级激活方式和运行时所有者。 | 现有暗色是给 `<html>` 加 class `dark`。要纳入设计系统的话，继续用这个 class，还是改成别的方式？我建议维持现状，不新建开关。 |
| 该 Scope 的 `kind` 应为 `section` 还是 `page`？ | `/showcase` 下面有一组自己的强调色，只作用这一块。要不要把它当成「这一区的特殊装修」登记？我建议登记，先不接到页面上。 |
| Token files contain no token values yet. | 目录已经建好，但还没有写入你确认过的颜色和间距。确认提案后我才会填进去。 |

## 选项怎么写

每个选择题固定四段，缺一不可：

1. 用一句话说清楚在问什么；
2. 2～4 个选项，其中一项标明「推荐」和一句理由；
3. 「不确定就选推荐项」；
4. 选完之后我会做什么、仍然不会做什么（例如：不会改页面、不会造暗色开关）。

证据冲突、边界重叠或 Theme 运行时所有者不清楚时，停在问卷里，不要把候选写成系统事实。
